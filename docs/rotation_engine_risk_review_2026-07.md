# 轮动引擎代码评审与风险修复报告（2026-07）

> 分支：`feature/rotation-strategy-v2`
> 触发：系统性代码评审（backend + scripts/rotation，7个AI审查agent，219次文件读取）
> 范围：数据管道可靠性、策略逻辑、代码质量、API安全、因子引擎、测试覆盖
> 后续：策略层回测揭示"赔率不对称"和"市场反转踏空"两个结构性问题并已修复验证

## 1. 背景

在对系统做全面代码评审后，进一步用 2021-01~2026-07 的滚动月度回测评估了轮动引擎
（`scripts/rotation/`）的实际表现，发现两类问题：

1. **工程正确性问题**：数据管道非原子写入、NaN数据透传、缓存bug、API无认证等
2. **策略结构性问题**：回测胜率61.2%看似不错，但89%的超额收益集中在2个月内，
   赢/输赔率不对称（0.83），且在市场反转（熊转牛）时系统性踏空5-17个交易日

本文档记录发现、修复方案和验证结果，供后续迭代参考，避免重复踩坑。

## 2. 代码评审发现（35项：3严重 / 14高危 / 15中危 / 3低危）

完整评审报告见 `artifacts/system-review-2026-07-27.md`（本地文件，data/artifacts同属
gitignore范围不随仓库同步）。以下是已修复的核心问题：

### 2.1 三个严重问题

| # | 问题 | 文件 | 影响 |
|---|------|------|------|
| 1 | 熔断器在权重已更新后才触发 | `scripts/rotation/engine.py` | 无法阻止导致亏损当日的调仓，熔断形同虚设 |
| 2 | Sharpe比率用`ddof=0`（总体标准差） | `scripts/rotation/metrics.py` | 系统性偏高约1.2%，且作为网格搜索目标函数，误导参数选择 |
| 3 | 全部API端点（含破坏性POST）无认证 | `backend/app/main.py` | 任何人可触发数据刷新、删除持仓状态 |

### 2.2 已修复的高危/中危问题

| 问题 | 修复方式 |
|------|---------|
| Parquet非原子写入 | `write_parquet`改为先写临时文件再`os.replace` |
| `collect_top_etfs`双文件替换非原子 | 写入同一临时目录后原子替换，成功后清理 |
| NaN收盘价静默透传 | 归一化器新增OHLC空值/非正价格拦截 |
| 猴子补丁`requests.get/post`线程不安全 | 改用独立`Session`+自定义超时，移除全局补丁 |
| 重试异常覆盖不全 | 扩展捕获`Timeout`、`ConnectionError`等瞬态异常 |
| AKShare空DataFrame无检测 | 新增空值检查，为空时抛异常触发重试 |
| 缓存`get_or_create`无法缓存None值 | 用哨兵对象`_MISSING`区分"未命中"与"缓存了None" |
| `pct_change()`两处调用不一致 | 统一为`pct_change(fill_method=None)` |
| CORS `allow_origins=["*"]` | 默认收紧为`localhost` |
| 流动性过滤器使用全历史均值（前视偏差） | 新增`cutoff_date`参数，支持窗口内过滤 |

## 3. 策略层核心发现：赔率不对称与市场反转踏空

修复上述工程问题后，用真实引擎跑了2021-01~2026-07的滚动月度回测（K=3固定持仓），
发现两个此前未被察觉的结构性问题。

### 3.1 问题一：赔率不对称（风险收益比不利）

| 指标 | 数值 |
|------|------|
| 月度胜率 | 61.2%（41/67月） |
| 赢时平均超额 | +4.53% |
| **输时平均超额** | **-5.49%** |
| **赔率比（赢/\|输\|）** | **0.83（<1，不利）** |
| 信息比率 | 0.33（需>0.5才算显著） |
| 89%累计超额来源 | 仅2/67个月（2025年7-8月） |

**根因定位**：`bull_boost=1.50`——牛市时权重乘以1.50，3只等权持仓总敞口达150%，
隐含杠杆但未扣除融资成本。当"判对方向、选错标的"时（如大盘涨但持仓的行业ETF跌），
150%敞口把亏损同比例放大，这正是"赢的次数多但输的时候更狠"的直接原因。

### 3.2 问题二：市场反转时的踏空

原regime判断仅用`MA10 < MA30`二元交叉，天然有5-10天滞后。逐日回放几次历史反转
事件，测量"从月初到系统开始加仓"所需交易日：

| 反转事件 | 大盘表现 | 旧逻辑反应 | 说明 |
|---------|---------|-----------|------|
| 2022-11反弹 | +6.19% | 第10个交易日才判牛 | 反弹前10天仅50%仓位参与 |
| 2023-01反弹 | +7.60% | 第4个交易日 | 滞后较小 |
| 2024-09暴涨 | +28.87% | 第17个交易日 | 反弹最肥的前17天几乎踏空 |

滚动月度统计也证实：牛市胜率仅48.5%（约等于随机），熊市胜率75.8%——系统本质是
**防守型策略，进攻端拖后腿**，且拖后腿的直接原因之一就是反转确认太慢。

## 4. 修复方案与实现

### 方案A：去杠杆（消除赔率不对称的主因）

`scripts/rotation/config.py`：所有`bull_boost`从1.20~1.50统一降为**1.00**
（`StrategyConfig`及全部5个`ClassConfig`资产类别实例），彻底取消牛市隐含杠杆。

同时在`scripts/rotation/engine.py`补充：若未来仍出现敞口>100%的场景（如
`bear_scale`/`bull_boost`被调回>1的值），按超额敞口×3%年化利率扣除融资成本，
不再让杠杆收益"免费"。

### 方案B：四信号投票regime检测（缩短反转确认滞后）

`scripts/rotation/engine.py`新增`_multi_signal_regime_scale()`，用四个信号投票
替代单一MA10/MA30判断：

| 信号 | 反应速度 | 权重 |
|------|---------|------|
| MA5 > MA20 | 快（2-3日） | 1票 |
| RSI(5) > 70 | 极快（1日） | 1票 |
| 3日涨幅 > 5% | 极快（1日） | 1票 |
| MA10 > MA30（原逻辑） | 慢（5-10日） | 1票 |

票数≥3→牛市模式（100%）；票数≤1→熊市模式（50%）；票数=2→**新增中性档（75%）**，
在反转确认过程中渐进加仓，而不是等慢速信号完全确认才动作。

### 熔断器时序修复

原逻辑先把`current_weights`更新为新目标权重，再检查是否触发熔断——即使触发，
新权重已经生效。修复为：熔断触发时**回退到触发前的旧权重**，真正阻止当日调仓，
而非仅影响次日。

## 5. 验证结果：新旧引擎对比回测

用同一份2021-2026数据、相同K=3配置，仅切换`bull_boost`和regime判断逻辑，跑
67个月的逐月对比（脚本：`scripts/compare_old_new.py`）。

### 5.1 整体指标

| 指标 | 新版（A+B） | 旧版 |
|------|-----------|------|
| 月度胜率 | 55.2% | 55.2%（未变） |
| 赢时平均超额 | +3.54% | +4.67% |
| **输时平均超额** | **-3.19%** | -4.41% |
| **赔率比** | **1.11** | 1.06 |
| **最差单月超额** | **-10.37%** | -12.84% |
| 67个月累计策略收益 | **+9.07%** | +6.78% |

胜率本身没变（仍是抛硬币水平的信号质量问题，A+B没有解决"选对标的"这件事），
但赢输幅度更对称、尾部风险更小、累计收益反而更高——**用适度降低单次爆发上限，
换取显著更低的尾部风险**。

### 5.2 反转事件响应速度改善（方案B的直接效果）

| 反转事件 | 旧版首次加仓 | 新版首次加仓 | 提前量 |
|---------|------------|------------|--------|
| 2022-11反弹 | 第10个交易日 | 第5个交易日 | **提前5天** |
| 2023-01反弹 | 第4个交易日 | 第3个交易日 | 提前1天 |
| 2024-09暴涨 | 第17个交易日 | 第14个交易日 | 提前3天 |

### 5.3 诚实的权衡

熊转牛/急涨月份（大盘单月>5%）的平均踏空对比中，新版（-4.10%）反而比旧版
（-3.29%）"看起来更差"——但这是被2025-08一个月拉偏的：旧版150%杠杆在那次真实
大牛市里吃满了收益（+32.79% vs 新版+19.66%），这正是我们要砍掉的"彩票式"收益。
**去杠杆的代价就是极端牛市月份少赚，这是有意为之的权衡，不是bug。**

同时用一次真实的历史复盘验证了这个权衡的方向是对的：2026-07-02半导体板块单日
集体跌8-9%，旧引擎（150%敞口）当日亏损-9.81%，新引擎（去杠杆后）在完全相同的
持仓和行情下亏损收窄到-4.90%。

## 6. 数据管道的一个教训：clean层与research层的耦合风险

刷新ETF数据时发现：`backend/app/jobs/collect_top_etfs.py`默认
`--lookback-days 365`（README文档命令和每日自动化工作流的标准参数）会让
`data/clean/etf_daily.parquet`里约90%的标的**丢失2019-2025深度历史**，只保留
最近一年——这是系统design intent（clean层是滚动窗口，服务于API/看板的"新鲜数据"），
但`scripts/rotation/`回测引擎依赖的`data/research/etf_daily_backtest.parquet`是
一份独立构建的深度历史快照。

如果直接用`scripts/build_backtest_data.py`从（已被365天窗口刷新过的）clean层
重建research数据集，会**用短窗口覆盖掉7年深度历史**，导致`min_history_days=1200`
等长历史过滤条件全部失效。

**正确做法**：增量合并而非整体重建——保留research层现有深度历史，只从clean层
补充比现有最新日期更新的交易日。已写成可复用脚本
`scripts/merge_recent_data.py`，内置与`normalize_etf_daily`一致的异常涨跌幅
校验（自动拒绝可疑新增数据）。

## 7. 仍然存在的风险（未解决，需要后续决策）

1. **月度胜率本身没有改善**（55.2%，A+B只优化了赢输的分布形状，没有让"选对标的"
   的能力变强）。信息比率仍然偏低，统计显著性不足以支撑"大多数情况下跑赢大盘"
   的强结论。
2. **收益集中度问题未根本解决**——只是降低了下行时的伤害，没有增加信号本身的
   稳定性。如果多信号regime投票的四个信号本身存在共线性（例如同涨同跌的市场里
   MA5/MA20和MA10/MA30几乎总是同步），中性档的"渐进"效果会打折扣，需要更长
   历史样本验证。
3. **月度胜率61.2%的样本量（67个月）在统计上仍然偏小**，尤其是"极端月份主导
   收益"的特征意味着少数几个月的样本外表现会大幅摆动整体结论。

## 9. 风险提示

1. 本报告的回测结论基于历史数据（2021-01~2026-07），历史表现不代表未来收益
2. A+B修复改善了尾部风险和赔率结构，但**没有把胜率不足50%的牛市表现变成显著
   优势**——如果后续要解决这个问题，需要在信号层（如何选中真正会涨的行业ETF）
   而非风控层（如何管理已选中标的的仓位）继续迭代
3. 本项目仍是研究工具，不构成投资建议，详见`README.md`投资风险说明
